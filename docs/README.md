# OctoAcme Project Management Docs

This README is the entry point for the project management process documentation in this repository. It provides a concise overview of OctoAcme's operating model and direct links to the detailed process guides in this `docs/` folder.

## Overview of OctoAcme project management processes

OctoAcme follows a lightweight, outcome-focused project management model built around a clear lifecycle: initiation, planning, execution, release, and retrospective. New initiatives begin with a short Project One-pager to confirm the problem, define success metrics, identify stakeholders, and decide whether to move forward. Once approved, work is transformed into a prioritized backlog, release plan, and milestone map with explicit ownership, dependencies, and acceptance criteria. During execution, the team uses a shared project board, iterative delivery cadence, and daily/weekly communication routines to keep work visible and accountable.

The operating model also defines core roles and responsibilities. Product Managers shape the strategy and priorities, Project Managers coordinate timelines, risks, and communication, Developers build and test the work, QA validates quality and acceptance criteria, and stakeholders provide input and approvals. Risks and dependencies are tracked in a simple Risk Register and escalated through defined paths when issues affect delivery or business outcomes. Communication is structured around standups, project reviews, stakeholder updates, and formal escalation when blockers or incidents require broader response.

Quality is treated as a first-class delivery concern. Teams are expected to use automated tests, CI checks, security scanning, and smoke testing for critical user flows before release. Pull requests are expected to be small, include issue references and acceptance criteria, and undergo review and approval before merge. Releases are managed with a checklist-driven process that includes staging validation, rollback planning, and post-deployment verification. The team also captures learnings after sprints, releases, and incidents through structured retrospectives so improvements are translated into backlog actions and tracked over time.
